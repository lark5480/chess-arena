## 📌 TL;DR（执行摘要）

- **整体结论：🔴 不通过（No-Go）** — 这份 PRD 结构完整、技术选型合理，但存在**一个贯穿全文的架构性根因**，不能直接进入开发。

## 1. 各成员核心结论

### 🔍 产品评审员（需求逻辑与实现成本）

- **核心判断：No-Go**，8 项阻塞问题澄清前不能开工。问题不在"想做什么"，而在"多处该定的规则没定"。
- **最致命的需求层缺陷**：
  - **P0/P1 优先级倒置** — P0 的"对局结束检测"明确包含**超时**，但计时器被放在 P1。P0 依赖一个还没做的 P1 能力，这是排期上的死结。
  - **颜色分配规则完全空白** — 谁执白？随机、先到先得、还是创建者可选？这是开局第一步就要用到的规则，全文无一字。
  - **和棋规则不完整** — P0 只写了"逼和（stalemate）"，漏了**50 步规则、三次重复局面、子力不足**。chess.js 都支持，但需求没声明要不要做、怎么提示，实现时必然拍脑袋。
  - **升变 UI 流程缺失** — P0 声明支持升变，但选皇后/车/象/马的交互弹窗一字未提。
  - **`/spectate` 页面自相矛盾** — §六 页面结构里列了观战页并标注 P2，但 §三 P2 功能表里根本没有"观战"这一项。
- **成本重估**："断线重连、状态一致性、悔棋状态机、移动端拖拽体验、时钟仲裁"这几项是典型工时黑洞，PRD 分别只给了半天到一天。**11 天 → 14–18 天**。
- **降级建议**：若必须 11 天交付 → 砍 P2 全量，P1 只留计时器 + 认输 + 求和，把悔棋、聊天、对局历史全部后置。

### 🛡️ 安全官（STRIDE + OWASP 双框架审计）

- **核心判断：3 项 🔴 严重架构缺陷 + 3 项 🟠 高危**，且 §13 风险表**零条安全条目**。
- **① 信任边界根本缺陷（🔴 A08/Tampering，§8.1）**：校验全在客户端。攻击者可绕过 `if(game.turn()!==myColor)` 直接调 `broadcastMove(任意san, 任意fen)`——**凭空造皇后、直接吃掉对方王、发 `{san:'Qe8#'}` 伪造将死**；还可直接 INSERT `game_results(winner='white')` 写一个胜利。安全官原话：客户端 chess.js 校验"只防自己手滑走错，防不了故意作弊"，**"防作弊"是错误定性**。
- **② 无身份凭证（🔴 A01/Spoofing）**：`players` 表无任何 secret 字段。拿到房间号即可冒充某方走棋、第三方可挤进满房、观战者能发 move 破坏对局、认输/求和无法证明"是本人"。
- **③ Supabase RLS 缺口（🔴 A01/A05）**：`NEXT_PUBLIC_SUPABASE_ANON_KEY` 设计上可公开——**前提是开启 RLS**。但 PRD 四张表全程未提 RLS，等于匿名 key 能对 rooms/players/moves/game_results 任意 CRUD，**相当于把数据库公开**。这是全文最危险的隐含缺口。
- **④ 房间号（🟠）**：`VARCHAR(6)` + 36 字符集 ≈ 21.7 亿空间，但**无速率限制**即可枚举探测进行中的对局；`UNIQUE` 碰撞会直接导致建房失败（DoS）；nanoid 未指定安全字母表。
- **⑦ 计时器篡改（🟠，补充发现）**：与①同源但落在独立的胜负判定上——攻击者可改本地 `timeLeft`、或利用**浏览器后台标签页节流**"冻结时间"变相无限时；判负由本端触发，对手无法验证。
- **务实分层**（针对练习项目性质）：
  - **必修**：服务端权威（或至少把 §8.1 更名为"规则校验"而非"防作弊"）、开启 RLS、轻量 `player_secret`、房间号限流
  - **建议修**：聊天/昵称 XSS 转义、API 限流、chess.js 锁正式版
  - **可接受但须在 PRD 注明"已知限制"**：内容审核、强加密 token、高级反滥用

### 🔧 调查员（技术可行性与边界条件）

- **核心判断：3 项开工前必改的架构决策**（改晚了要重写），6 项高优先级可迭代项。
- **🔴「以 FEN 为唯一真相源」是逻辑自相矛盾**（§13）：FEN 由**发送方客户端自己算出来**，接收方无从校验。一个由单方面声明、对方无法验证的值，在定义上就不能叫"唯一真相源"。这句话给了读者虚假的安全感。
- **🔴 双写不一致**（§7.2 广播 + §9 `/api/moves`）：走棋广播和持久化是**两条独立链路，无事务、无对账**。广播成功但持久化失败（或反之）时，断线重连从 DB 读到的 FEN 会落后/超前于对手的真实棋盘。
- **🔴 计时器注释 ≠ 实现**（§8.3）：纯客户端 `setInterval` 判负，失效场景全集——两端时钟漂移、后台标签页/移动端锁屏节流导致时间冻结、**超时由哪一方裁定的争议**（双方各自判会产生"我认为你超时/你认为我没超时"）、断线期间是否继续计时未定义、网络延迟算谁的时间。正解是服务端权威 deadline 时间戳 + 客户端只做渲染插值。
- **🟠 broadcast 被误当可靠信道**：Supabase Realtime broadcast 是 **fire-and-forget，无 ack、无重传、不保证顺序**，断线期间消息直接丢失（不像 postgres_changes 有 DB 兜底）。PRD 全程按可靠信道使用。
- **🟠 `game_results` 以 `room_id` 为主键 → 数据模型层面封死了 rematch**：一个房间只能存一局结果。而 M4 里提到了"重新开始"。这是数据模型对产品能力的**隐性封杀**，产品侧还没意识到。
- **🟠 `players` 缺 `(room_id, color)` 唯一约束、`moves` 缺 `(room_id, move_number)` 唯一约束** → 重复走棋/消息重投会插入脏数据（幂等性缺失）。
- **🟠 "延迟 < 500ms" 在国内网络访问 Supabase 海外区大概率不可达**，且 PRD 完全未提区域选择。
- **🟡 细节**：`fen VARCHAR(100)` 实测约 90 字符不会截断但属 magic number，建议 `TEXT`；`TIMESTAMP` 应为 `TIMESTAMPTZ`；架构图里的 **Edge Functions 全文无任何用途说明**（悬空组件）；Vercel 冷启动会影响"10 秒开局"指标；Supabase 免费项目 **7 天无活动自动暂停**（技术限制未说明）。
- **风险表需从 4 条补到约 14 条**，且"chess.js 经过大量测试，可信赖"这一结论**对 beta 版本并不成立**。
